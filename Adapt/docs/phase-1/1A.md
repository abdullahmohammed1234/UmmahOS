1. Purpose

Phase 1A converts the ADAPT workflow into a collection of explicit AI prompt contracts.

The objective is to ensure that every LLM interaction is:

deterministic in structure
clearly scoped
reproducible
testable
explainable
independently evaluable
replaceable without redesigning the entire system

ADAPT should not rely on a single large prompt that attempts to perform the entire tutoring process.

Instead, the system decomposes adaptive tutoring into specialized decisions.

2. Core Principle

ADAPT is based on the hypothesis:

A tutoring system can provide more useful learning interactions when it continuously analyzes a learner's demonstrated understanding and uses that information to generate the next challenge.

The system therefore follows:

Learner
   ↓
Question / Learning Goal
   ↓
Learner State
   ↓
Challenge Generation
   ↓
Learner Response
   ↓
Response Analysis
   ↓
Misconception Diagnosis
   ↓
Intervention / Feedback
   ↓
Updated Learner State
   ↓
Next Challenge

The critical property is the feedback loop.

The system should not merely generate a sequence of questions.

It should use the student's previous response to determine what happens next.

3. LLM Node Architecture

The MVP will use the following logical LLM nodes:

N1 — Learner Profiler
N2 — Challenge Generator
N3 — Response Analyzer
N4 — Misconception Diagnoser
N5 — Intervention Generator
N6 — Difficulty Adapter

However, these do not necessarily need to be six separate API calls.

During implementation we will test whether some nodes can be safely combined.

The logical separation exists first for:

prompt engineering
evaluation
explainability
experimentation

We should not add model calls simply to make the architecture appear more sophisticated.

4. Global Prompt Rules

Every ADAPT prompt should follow these principles.

4.1 No unsupported assumptions

The model must distinguish:

Observed
Inferred
Unknown

It must not invent information about the learner.

4.2 Structured output

Where machine-readable output is required, the model must return JSON conforming to the specified schema.

No conversational text should be included outside the schema.

4.3 Evidence-based learner modeling

The system should infer learner knowledge from:

answers
explanations
mistakes
response confidence
repeated patterns

It should not infer ability from arbitrary characteristics.

4.4 Minimal intervention

ADAPT should avoid immediately explaining the answer.

The system should prefer:

diagnose → challenge → hint → explain

rather than:

student struggles → immediately provide solution

when continued practice is pedagogically appropriate.

5. N1 — Learner Profiler
Purpose

Create or update a structured representation of what the learner appears to understand.

Input
{
  "learning_goal": "...",
  "topic": "...",
  "previous_interactions": [],
  "current_response": null
}
Output
{
  "concepts": [
    {
      "concept": "...",
      "status": "unknown | emerging | demonstrated | inconsistent",
      "confidence": 0.0,
      "evidence": []
    }
  ],
  "strengths": [],
  "weaknesses": [],
  "open_questions": []
}
Prompt Contract
System Prompt
You are the Learner Profiler for ADAPT, an adaptive learning system.


Your task is to construct a cautious representation of the learner's demonstrated
understanding from the provided interaction history.


Only infer knowledge that is supported by the learner's responses.


For every concept, distinguish between:
- unknown
- emerging
- demonstrated
- inconsistent


Do not assume mastery merely because the learner answered one question correctly.


Do not diagnose a misconception unless the available evidence supports it.


Return only valid JSON matching the requested schema.
Failure Modes

Potential failures:

assuming mastery from one correct answer
treating guessing as understanding
over-interpreting short responses
confusing vocabulary familiarity with conceptual understanding
carrying an old misconception forward after it has been corrected
6. N2 — Challenge Generator
Purpose

Generate the next learning challenge based on the learner's current state.

This is one of the most important nodes in ADAPT.

The question should be selected because it provides useful information about the learner.

Input
{
  "learning_goal": "...",
  "learner_state": {},
  "recent_interactions": [],
  "target_difficulty": "...",
  "constraints": {}
}
Output
{
  "challenge": {
    "question": "...",
    "type": "...",
    "difficulty": 0,
    "target_concepts": []
  },
  "expected_evidence": [],
  "reasoning": "..."
}
Prompt
You are the Challenge Generator for ADAPT.


Generate one learning challenge that tests the learner's current understanding
while providing useful evidence about what they know and do not know.


Use the learner state and recent interactions.


The challenge must:
1. target one or more relevant concepts,
2. be appropriate for the learner's estimated level,
3. reveal meaningful evidence of understanding,
4. avoid unnecessarily repeating questions,
5. avoid introducing concepts that are outside the current learning goal.


Do not reveal the answer.


Do not generate a challenge merely because it looks difficult.


The challenge should have a clear pedagogical purpose.


Return only valid JSON.
7. N3 — Response Analyzer
Purpose

Analyze the learner's answer without immediately deciding how to teach them.

This separation is important.

The analyzer asks:

What happened?

The diagnostician asks:

Why did it happen?

Input
{
  "question": "...",
  "expected_concepts": [],
  "learner_answer": "...",
  "learner_confidence": null
}
Output
{
  "correctness": "correct | partially_correct | incorrect | unclear",
  "demonstrated_concepts": [],
  "missing_concepts": [],
  "errors": [],
  "evidence_spans": [],
  "confidence": 0.0
}
Prompt
You are the Response Analyzer for ADAPT.


Analyze the learner's response against the challenge.


Determine:
- whether the response is correct,
- which concepts are demonstrated,
- which concepts are missing,
- what errors are observable.


Do not invent a psychological explanation for the learner's mistake.


Do not assume why an error occurred.


Your role is observation and analysis, not diagnosis.


Return only valid JSON.
8. N4 — Misconception Diagnoser
Purpose

Determine whether an observed error represents a meaningful misconception.

This is one of the most important distinctions in the system.

A wrong answer does not automatically mean the learner has a misconception.

Input
{
  "question": "...",
  "learner_answer": "...",
  "response_analysis": {},
  "previous_errors": [],
  "concept_map": []
}
Output
{
  "diagnosis": "no_misconception | possible_misconception | likely_misconception | insufficient_evidence",
  "concept": "...",
  "description": "...",
  "evidence": [],
  "alternative_explanations": [],
  "recommended_action": "..."
}
Prompt
You are the Misconception Diagnoser for ADAPT.


Determine whether the learner's observed error provides evidence of a
conceptual misconception.


A single incorrect answer is not sufficient evidence of a stable misconception
unless the response itself clearly reveals the incorrect concept.


Consider alternative explanations such as:
- calculation error,
- misunderstanding of wording,
- incomplete response,
- accidental mistake,
- insufficient information.


Do not over-diagnose.


If evidence is insufficient, explicitly say so.


Return only valid JSON.
9. N5 — Intervention Generator
Purpose

Determine the most useful pedagogical response after analyzing the learner.

Possible interventions:

NEXT_CHALLENGE
HINT
TARGETED_EXPLANATION
SIMPLER_EXAMPLE
CONTRASTING_EXAMPLE
RETRY
Input
{
  "learning_goal": "...",
  "learner_state": {},
  "response_analysis": {},
  "misconception": {},
  "recent_interventions": []
}
Output
{
  "intervention": "next_challenge | hint | targeted_explanation | simpler_example | contrasting_example | retry",
  "content": "...",
  "target_concept": "...",
  "reason": "..."
}
Prompt
You are the Intervention Generator for ADAPT.


Select the smallest intervention likely to help the learner progress.


Use the learner state, response analysis, and misconception diagnosis.


Prefer active learning over passive explanation.


Do not reveal the complete answer when a useful hint, retry, or targeted example
would allow the learner to reason toward the answer themselves.


If the learner has demonstrated understanding, avoid unnecessary remediation.


Return only valid JSON.
10. N6 — Difficulty Adapter
Purpose

Determine how the next challenge should change in difficulty.

Input
{
  "current_difficulty": 3,
  "response_analysis": {},
  "learner_state": {},
  "recent_difficulties": []
}
Output
{
  "next_difficulty": 0,
  "direction": "increase | maintain | decrease",
  "reason": "...",
  "target_concepts": []
}
Prompt
You are the Difficulty Adapter for ADAPT.


Adjust the challenge difficulty based on demonstrated learner performance.


Do not increase difficulty solely because an answer was correct.


Consider:
- correctness,
- consistency,
- conceptual understanding,
- recent performance,
- complexity of the reasoning required.


Avoid large difficulty changes unless there is strong evidence.


Return only valid JSON.
11. The Most Important Design Decision

We should not assume these six LLM calls are optimal.

The first implementation should test at least two architectures.

Architecture A — Specialized
Profiler
   ↓
Challenge Generator
   ↓
Response Analyzer
   ↓
Diagnoser
   ↓
Intervention Generator
   ↓
Difficulty Adapter

Advantages:

highly explainable
easy to evaluate
clear prompt contracts

Disadvantages:

expensive
slower
more opportunities for errors
Architecture B — Consolidated
Learner State
     ↓
Adaptive Tutor
     ↓
Challenge / Feedback / Difficulty

with perhaps only:

Response Analyzer

as a separate verification step.

Advantages:

faster
cheaper
simpler

Disadvantages:

harder to determine which reasoning failed
less modular
potentially weaker prompt specialization
12. Experimental Hypothesis

Phase 1A does not assume Architecture A is better.

We will test:

Does decomposing adaptive tutoring into specialized prompt contracts produce measurably better adaptation than a consolidated tutoring prompt?

This is important.

The hackathon judges don't need to believe our architecture is superior because it contains more nodes.

We need to demonstrate that the structure produces useful behavior.

13. ADAPT State

The central object passed between workflow stages should be:

{
  "learner_id": "...",
  "learning_goal": "...",
  "concepts": [],
  "current_difficulty": 1,
  "strengths": [],
  "weaknesses": [],
  "known_misconceptions": [],
  "recent_interactions": [],
  "confidence": 0.0
}

The exact schema will be finalized during the next phase.

14. Human Input Contract

The human should primarily provide:

Learning goal
Topic
Optional current level
Optional constraints

Example:

"I want to learn recursion in Python."

ADAPT should then determine what the learner needs rather than asking the learner to manually configure a complicated lesson.

15. Human Checkpoint

The primary human checkpoint should occur when ADAPT detects:

high uncertainty
        OR
conflicting evidence
        OR
multiple plausible learning paths

The interface could ask:

What would you like to focus on?

[ Understand the concept ]


[ Practice problems ]


[ Fix the mistake I keep making ]

This gives the learner meaningful control without requiring them to manage the AI workflow.

16. Anti-Hallucination / Reliability Rules

The prompts must explicitly prevent the system from pretending to know the learner.

The model must distinguish:

Observed:
"The student wrote X."


Inference:
"This may indicate Y."


Unknown:
"There is insufficient evidence."

This is critical because an adaptive tutor can actually become worse if it builds an incorrect learner model.

17. Prompt Evaluation

Every prompt will eventually be tested against adversarial cases.

For example:

Case A — Correct answer, wrong reasoning
Answer: 42
Explanation: mathematically invalid reasoning

Expected behavior:

correctness = partially_correct / inconsistent

rather than:

mastery
Case B — Wrong answer, correct concept

A student understands the method but makes an arithmetic error.

Expected:

possible procedural error

rather than:

conceptual misconception
Case C — Guessing

The student gives the correct answer but cannot explain it.

Expected:

insufficient evidence of mastery
Case D — Ambiguous response

The student writes:

"I think it's because it goes back."

Expected:

unclear

rather than an invented diagnosis.

18. Prompt Versioning

All prompts will be version controlled.

Example:

ADAPT-P01-v0.1
ADAPT-P01-v0.2
ADAPT-P01-v0.3

Once experimentally validated:

ADAPT-P01-v1.0

is frozen for the benchmark.

Prompt changes after benchmark execution must create a new version.

19. Phase 1A Success Criteria

Phase 1A is complete when:

Every LLM node has a defined purpose.
Every node has explicit inputs.
Every node has explicit outputs.
Outputs have machine-readable structure where necessary.
Prompts contain explicit constraints.
Failure modes have been identified.
Human intervention has a defined purpose.
Architecture alternatives have been identified.
Prompt versioning has been established.
Initial adversarial test cases have been defined.
No claim has been made that the workflow is superior before testing.

21. Critical Phase 1A Question

Before proceeding, we need to test one fundamental assumption:

Does adaptive tutoring actually require multiple specialized LLM stages?

The answer should come from experiments, not architecture aesthetics.

Therefore the next stage will not simply be:

"Let's code all six agents."

Instead, we will construct Prompt Contract Destruction Tests.

We will deliberately attack the prompts with cases such as:

correct answer + incorrect reasoning
incorrect answer + correct reasoning
guessing
ambiguous responses
contradictory answers
repeated misconceptions
sudden improvement
inconsistent performance
adversarial student input
questions outside the learning objective

If the contracts survive these tests, we freeze them.

If they fail, we change the architecture before writing the application.
