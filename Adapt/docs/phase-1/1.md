ADAPT — Phase 1: ML Workflow & Prompt Architecture

Status: Phase 1 begins now.

We are now moving from "What should we compete with?" to:

"Exactly how does ADAPT think, what does every prompt do, what information flows between nodes, and how will we prove the workflow works?"

The goal is not to build the UI yet and not to maximize the number of LLM calls.

The goal is to produce a workflow that is:

reproducible;
measurable;
explainable;
prompt-engineering focused;
robust to LLM mistakes;
feasible to implement;
compelling in the hackathon demo.
1. Phase 1 Architectural Decision

After Phase 0.5, we should not build a generic "adaptive tutor."

The system we are building is:

ADAPT — Diagnostic Challenge Selection

An AI learning workflow that interprets student responses as evidence about their conceptual understanding, forms and tests misconception hypotheses, maintains an explicit learner state, and selects the next challenge based on that state.

The fundamental loop is:

2. The Most Important Architectural Principle

There are two different things happening:

Diagnosis

What does the student's response tell us?

and:

Intervention

What should we do about it?

We must not combine these into one vague prompt.

Otherwise the model can jump directly from:

"Student got it wrong"

to:

"Give them an easier question."

Instead:

Response
   ↓
Evidence
   ↓
Diagnosis
   ↓
Uncertainty
   ↓
Decision
   ↓
Intervention

That separation is central to the credibility of ADAPT.

3. Initial MVP Domain
Computer Science

We will initially build around CS education.

However, we should not hard-code the architecture around recursion.

Recursion will be our initial demonstration domain because it provides excellent examples of conceptual misconceptions.

The workflow should eventually support:

Recursion
Big-O
Arrays
Pointers/references
Data structures
Debugging
Algorithms

But we will initially validate it on a much smaller set.

│

│

This is our initial contract, not something we should blindly treat as final.

{
  "topic": "recursion",
  "concepts": [
    {
      "id": "recursive_call",
      "status": "partial",
      "confidence": 0.72,
      "evidence": [
        {
          "challenge_id": "rec-001",
          "observation": "Student correctly identified the recursive call."
        }
      ]
    },
    {
      "id": "return_value_tracking",
      "status": "uncertain",
      "confidence": 0.43,
      "evidence": [
        {
          "challenge_id": "rec-001",

        }
      ]
    }
  ],
  "misconceptions": [
    {
      "id": "return-value-confusion",
      "status": "suspected",

But there's an important rule:

Confidence is the system's confidence in its diagnosis, not a measurement of the student's intelligence or actual mastery.

We should make this distinction explicit in the documentation.

8. Confidence

Use a bounded value:

0.0 → 1.0

But don't treat it as calibrated probability yet.

Instead:

Diagnostic confidence score

The documentation should explicitly say this is a model-generated confidence signal unless we later calibrate it empirically.

9. Node 1 — Challenge Generator

This is where the learning interaction begins.

Purpose

Generate a challenge appropriate for the learner's current state.

Input
Topic
Learner state
Target concept
Difficulty
Intervention strategy
Previous challenges
Output

A structured challenge.

Challenge schema
{
  "challenge_id": "rec-002",
  "concept": "return_value_tracking",
  "difficulty": "intermediate",
  "type": "code_trace",
  "prompt": "What value does this function return when n = 3?",
  "code": "...",
  "expected_skill": "trace recursive return values",
  "diagnostic_target": "return-value-tracking"
}

The critical field is:

diagnostic_target

That tells the evaluator what the challenge was intended to reveal.

10. Challenge Types

ADAPT should initially support a controlled set.

1. Multiple choice

Useful for isolating concepts.

2. Code tracing

Excellent for CS.

3. Debugging

Useful for identifying procedural misconceptions.

4. Short answer

Tests conceptual understanding.

5. Explanation

Tests whether the learner can articulate reasoning.

6. Prediction

Useful for code and algorithms.

11. Prompt Contract — Challenge Generator

Conceptually:

SYSTEM


You are the challenge-generation component of ADAPT.


Your job is not to teach the student directly.


Your job is to create one challenge that is appropriate for the
student's current learner state and useful for evaluating or
strengthening a specific concept.


You must:
- target the specified concept;
- respect the difficulty;
- avoid repeating recent challenges;
- avoid testing concepts not relevant to the current intervention;

Return only the required structured output.

12. Node 2 — Response Analyzer

Now the student responds.

The response analyzer asks:

What objectively happened?

This is deliberately different from immediately diagnosing the misconception.

Input
Challenge
Student response
Expected answer
Expected reasoning
Learner state
Output
{
  "correctness": "incorrect",
  "partial_credit": "substantial",
  "observations": [
    "Student correctly identified the recursive call.",
    "Student incorrectly predicted the returned value."
  ],
  "reasoning_quality": "partial",
  "error_type": "conceptual_or_reasoning",
  "evidence": [
    "Student stated that each recursive call returns independently."
  ]
}
13. Why Separate Response Analysis?

Because:

Observation ≠ interpretation.

Example:

Observation

Student predicted 16 instead of 24.

Interpretation

Student doesn't understand multiplication.

Could be completely wrong.

Maybe the student simply made an arithmetic mistake.

The response analyzer should preserve the observable evidence before the diagnostic model interprets it.

14. Node 3 — Misconception Hypothesis

Now we ask:

What conceptual model could explain the student's response?

This is one of ADAPT's most important prompt-engineering nodes.

Input
Challenge
Student response
Response analysis
Learner state
Concept
Output
{
  "hypotheses": [
    {
      "type": "return_value_tracking",
      "description": "Student may not understand how recursive return values propagate.",
      "confidence": 0.67,
      "supporting_evidence": [
        "Student correctly identified recursive calls.",
        "Student incorrectly described the return sequence."
      ]
    },
    {
      "type": "arithmetic_error",
      "description": "The error may be procedural rather than conceptual.",
      "confidence": 0.29,
      "supporting_evidence": [
        "The student's explanation otherwise reflects the correct recursive structure."
      ]
    }
  ]
}

Notice something important.

We don't force the model to produce one answer.

We allow competing hypotheses.

That makes ADAPT more robust.

15. Node 4 — Uncertainty Assessment

This node asks:

Do we have enough evidence to act on the diagnosis?

This is where ADAPT becomes more interesting than a basic AI tutor.

Possible output
{
  "confidence": 0.67,
  "uncertainty_level": "moderate",
  "action": "test_diagnosis",
  "reason": "Two explanations remain plausible."
}
16. Three Uncertainty Levels
HIGH CONFIDENCE
      ↓
Targeted intervention


MEDIUM CONFIDENCE
      ↓
Diagnostic challenge


LOW CONFIDENCE
      ↓
Collect more evidence

This prevents the AI from confidently treating every mistake as a misconception.

17. Node 5 — Intervention Selector

This is the decision layer.

Possible actions:

DIAGNOSTIC
REMEDIATE
REINFORCE
ADVANCE
CHANGE_REPRESENTATION
DECREASE_DIFFICULTY
INCREASE_DIFFICULTY
18. Intervention Decision Table

We should have deterministic guardrails around the LLM.

Condition	Suggested action
Diagnosis uncertain	DIAGNOSTIC
Strong misconception evidence	REMEDIATE
Concept partially understood	REINFORCE
Repeated mastery	ADVANCE
Repeated failure	CHANGE_REPRESENTATION
Challenge clearly too difficult	DECREASE_DIFFICULTY
Strong performance	INCREASE_DIFFICULTY

The LLM can recommend an intervention, but the system can enforce basic safety rules.

This is important.

We don't want:

"GPT decided to give an advanced problem."

without any structural control.

24. But We Have Too Many Nodes

This is intentional for Phase 1.

Now we challenge the architecture.

Some of these may ultimately be merged.

For example:

Response Analyzer
+
Misconception Hypothesis

could potentially become one structured LLM call.

Likewise:

Intervention Selector
+
Adaptation Policy

could potentially be partly deterministic.

We will not keep nodes merely because they look impressive in the flowchart.

25. Proposed LLM vs Deterministic Responsibilities

This is a major architectural decision.

Component	LLM?	Why
Challenge generation	✅	Open-ended generation
Response analysis	✅	Natural language/code reasoning
Misconception diagnosis	✅	Requires interpretation
Uncertainty	✅	Evidence-based judgment
Intervention selection	⚠️	LLM recommendation + rules
Learner state update	⚠️	Structured transformation
Difficulty guardrails	❌/⚠️	Prefer deterministic rules
Schema validation	❌	Code
Score calculation	❌	Code
Benchmark scoring	❌	Code

This is important.

Not everything needs to be an LLM.

26. Model Strategy

We should initially use one strong LLM for the workflow.

Do not start with:

GPT + Gemini + Claude + Llama + five agents.

That adds complexity without proving anything.

Our initial experiment should isolate:

Does the workflow improve the result?

rather than:

Which model is best?

27. Why One Model Is Better Initially

Using the same model across nodes gives us a cleaner experiment:

Baseline:
Model X + single prompt


ADAPT:
Model X + structured workflow

Then the difference is much more attributable to the workflow.

This is scientifically cleaner.

28. Prompt Engineering Principle

Every prompt should have:

ROLE
OBJECTIVE
CONTEXT
INPUT CONTRACT
DECISION RULES
OUTPUT SCHEMA
CONSTRAINTS
FAILURE HANDLING

Avoid prompts like:

"Analyze the student's answer and figure out what they don't understand."

Instead:

"Identify observable evidence first. Generate up to three competing misconception hypotheses. For each hypothesis provide supporting evidence and confidence. Do not infer a misconception when the evidence is insufficient."

Much stronger.

29. Prompt Contract Example
Misconception Diagnoser
Role

You are the misconception-diagnosis component of an adaptive learning system.

Objective

Infer plausible conceptual explanations for the student's response.

Rules
Separate observations from interpretations.
Do not assume every incorrect answer represents a misconception.
Consider procedural errors.
Consider ambiguity.
Generate competing hypotheses where appropriate.
Provide evidence for every hypothesis.
Assign diagnostic confidence.
If evidence is insufficient, explicitly say so.
Output

Structured JSON.

This becomes part of our eventual documentation.

30. Structured Output Is Critical

The system should not rely on parsing prose.

Every node should return machine-readable output.

For example:

{
  "status": "uncertain",
  "hypotheses": [],
  "confidence": 0.0,
  "recommended_action": "diagnostic"
}

That makes the workflow reproducible.

31. Guardrails

Every LLM output should be validated.

For example:

LLM
 ↓
JSON parser
 ↓
Schema validation
 ↓
Valid?
 ├── YES → next node
 └── NO → repair/retry

We should never allow malformed model output to silently corrupt learner state.

32. Challenge Validation

Generated challenges should also be checked.

We need to verify:

correct answer exists;
difficulty matches requested level;
challenge matches concept;
no accidental ambiguity;
no duplicate;
code compiles where applicable.

This is particularly important for the demo.

33. A Critical Design Decision: Don't Let the AI Grade Itself Blindly

For objective CS questions, whenever possible:

Student code
      ↓
Execution / deterministic evaluation
      ↓
Correctness

rather than:

Student code
      ↓
LLM
      ↓
"Looks correct."

The LLM can interpret the reasoning, but deterministic evaluation should handle what can be determined deterministically.

34. Initial Question Evaluation

53. The Adaptation Loop

The complete logical algorithm is:

1. Load learner state.


2. Generate challenge.


3. Receive student response.


4. Analyze observable response.


5. Generate misconception hypotheses.


6. Estimate diagnostic confidence.


7. If confidence is insufficient:
       generate diagnostic challenge.


8. If misconception is supported:
       generate targeted remediation.


9. If learner demonstrates mastery:
       increase difficulty.


10. If repeated failure:
       change representation or reduce granularity.


11. Update learner state.


12. Repeat.


13. Eventually run transfer assessment.

That's the core ADAPT algorithm.

55. One Architectural Change I Recommend

Although we have shown seven conceptual stages, I don't want seven independent LLM calls by default.

The first implementation should investigate whether we can use:

LLM Call A

Response analysis + misconception hypotheses + uncertainty

and:

LLM Call B

Intervention/challenge generation

with deterministic state management between them.

Potentially:

Student response
      ↓
LLM A
      ↓
Structured diagnosis
      ↓
Deterministic state/policy
      ↓
LLM B
      ↓
Next challenge

This could be substantially cheaper, faster, and more reliable.

We can split them later if testing demonstrates that separation improves quality.

The final architecture should be determined by experiments, not by how impressive the diagram looks.

57. Phase 1 Testing Strategy

Before building the full frontend:

Test 1 — Diagnosis

Give ADAPT 10 known learner responses.

Measure:

Does it identify the intended misconception?

Test 2 — False diagnosis

Give it responses where the error is merely arithmetic/procedural.

Measure:

Does it avoid inventing a conceptual misconception?

Test 3 — Ambiguity

Give it ambiguous responses.

Measure:

Does it lower confidence and seek more evidence?

Test 4 — Adaptation

Give a sequence of responses.

Measure:

Does the next challenge actually respond to the learner state?

Test 5 — Difficulty

Give increasingly correct responses.

Measure:

Does difficulty increase appropriately?

Test 6 — Recovery

Give repeated incorrect responses.

Measure:

Does the system change representation instead of endlessly repeating similar questions?

58. The Most Important Test
Test 7 — Counterfactual

Give two students:

Student A

Understands recursion but makes arithmetic errors.

Student B

Has a return-value misconception.

They may both initially answer incorrectly.

ADAPT should eventually choose different interventions.

If it gives both students essentially the same next question:

Our adaptation mechanism isn't actually working.

This is an excellent benchmark case.
