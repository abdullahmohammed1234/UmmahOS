ADAPT — Phase 0.5: Strategy Destruction Test

Objective: Try to kill ADAPT before we invest serious build time.

I’m going to evaluate it as if I were a skeptical Reverie Hacks judge who has already seen 20+ AI tutor projects.

The standard is not:

“Can we build this?”

The standard is:

“Is this sufficiently differentiated, technically defensible, measurable, and impressive enough to compete for one of the six internship opportunities?”

0. Verdict First
ADAPT survives Phase 0.5 — but NOT in its original form.

The basic idea:

“AI identifies your weakness and generates the next question.”

is not sufficiently novel by itself.

A good team could build that with a strong system prompt in a day.

However, there is a much stronger version hiding inside it.

The project should become:

An AI learning system that treats every student response as diagnostic evidence and uses that evidence to select the most informative next challenge.

The critical concept becomes:

Diagnostic Challenge Selection

Not:

adaptive tutoring.

Not:

AI tutor.

Not:

personalized education.

But:

What should the AI ask this student next, given what their previous answer revealed?

That is our technical centerpiece.

1. Attack #1 — "Isn't this just ChatGPT with a tutoring prompt?"
Judge:

"I can open ChatGPT and say:
'Act as a tutor. Ask me questions, analyze my mistakes, and adapt your next question based on my weaknesses.'
Why do I need ADAPT?"

Initial verdict

This is a legitimate threat.

If ADAPT simply uses:

Student answer
↓
LLM
↓
Generate next question

then we lose.

2. Counterargument

Our system needs to explicitly separate:

OBSERVATION
    ↓
DIAGNOSIS
    ↓
LEARNER STATE
    ↓
DECISION
    ↓
CHALLENGE

For example:

Student response

"The function returns 4 because the recursive function calls itself four times."

ADAPT doesn't simply generate another question.

It creates:

{
  "observations": [
    "Understands that recursion involves repeated calls",
    "Incorrectly equates number of calls with returned value"
  ],
  "suspected_misconception": {
    "type": "return_value_tracking",
    "confidence": "medium"
  },
  "recommended_intervention": "trace_return_values"
}

Then the challenge generator receives that state.

That is a materially different architecture.

3. But Here's the Problem

A judge could respond:

"That's just structured prompting."

And they'd be partly right.

Therefore:

Prompt structure alone cannot be our innovation claim.

Our innovation must be the workflow + experiment.

We are testing whether:

Explicit diagnostic state + targeted challenge selection

produces better learning outcomes than:

single-prompt tutoring.

That's much stronger.

4. Attack #2 — "Is adaptive learning even new?"
Judge:

"Adaptive learning has existed for decades. Khan Academy does this. Intelligent tutoring systems do this. What's new?"

Verdict

Correct.

We absolutely must not claim adaptive learning itself is novel.

Instead:

Our contribution is the hackathon-scale experiment:

Can an LLM-driven prompt workflow dynamically infer a learner's conceptual state from natural-language/code responses and use that state to select the next diagnostic challenge?

That's narrower.

And much more defensible.

5. Attack #3 — "Why does this need an LLM?"

This is a dangerous question.

A judge could say:

"Couldn't you just build a decision tree?"

Absolutely.

For a controlled subject:

If answer wrong → easier question.
If answer correct → harder question.

That's trivial.

So ADAPT needs to do something that deterministic rules struggle with.

6. Our Answer

Students don't always make clean binary mistakes.

Consider:

"The function returns 8 because it keeps multiplying until n reaches zero."

There are several possible interpretations.

The system needs to reason about:

what the student understands;
what they misunderstood;
what misconception could produce this answer;
whether the error is conceptual or procedural;
what evidence supports the diagnosis.

Natural-language reasoning makes LLMs useful here.

7. But This Creates Another Risk

LLMs can be wrong about the student's misconception.

This is probably our biggest technical weakness.

Imagine:

Student makes arithmetic mistake
        ↓
AI thinks conceptual misconception
        ↓
AI gives remedial questions
        ↓
Student gets bored

That's disastrous.

Therefore we need explicit uncertainty.

8. New Requirement: Diagnostic Confidence

Every diagnosis should have:

Diagnosis
Confidence
Evidence
Alternative explanations

For example:

{
  "primary_diagnosis": "return_value_tracking",
  "confidence": 0.71,
  "evidence": [
    "Student correctly identified recursive call",
    "Student incorrectly predicted return propagation"
  ],
  "alternative": "arithmetic_error"
}

Now the system can decide:

Confidence isn't high enough.

Instead of aggressively adapting, it can run another diagnostic challenge.

This is much more interesting.

9. Attack #4 — "What if the AI is wrong?"

This is actually an opportunity.

A weak AI tutor says:

"You don't understand recursion."

ADAPT should say:

"I think you may be struggling with return-value tracing, but I'm not certain. Let's test that."

That transforms uncertainty into another learning interaction.

10. New Core Principle
ADAPT should not merely diagnose.

It should:

Test its diagnosis.

That gives us a much stronger loop:

Student response
       ↓
Hypothesis about misconception
       ↓
Confidence
       ↓
Diagnostic challenge
       ↓
New evidence
       ↓
Confirm / reject hypothesis
       ↓
Adapt

Now the system isn't blindly trusting its own diagnosis.

That's considerably stronger.

11. Attack #5 — "You're just making the AI ask more questions."

This is another serious problem.

More questions ≠ better learning.

If ADAPT requires:

15 questions to teach something ChatGPT explains in 2 minutes,

that's not impressive.

We therefore need another optimization objective:

Information gain per challenge.

The next challenge should ideally:

help the student learn;
reveal something about their understanding.
12. New Core Concept
Diagnostic value

Every challenge can conceptually have:

Learning value
+
Diagnostic value

We don't necessarily need to mathematically calculate these in MVP.

But our workflow can explicitly ask:

"What uncertainty about the learner would this challenge resolve?"

Example:

Challenge A

"What is recursion?"

Low diagnostic value.

Challenge B

"What does this function return?"

Higher diagnostic value.

Challenge C

"Which line executes immediately after the recursive call returns?"

Very high diagnostic value for call-stack understanding.

13. Attack #6 — "How do you know the student actually learned?"

This could kill the entire project if we don't handle it.

A student successfully answering:

"What is 4!?"

doesn't prove they learned recursion.

Therefore:

We need transfer tests.
14. Transfer Evaluation

Suppose ADAPT teaches:

factorial recursion

The final test could involve:

Fibonacci recursion

or:

recursive tree traversal

The surface problem changes.

The underlying concept remains.

If the student succeeds, we have stronger evidence of learning.

16. Attack #7 — "Your benchmark is biased."

Absolutely possible.

If we create questions that are perfectly suited to ADAPT, the results are meaningless.

Therefore:

Benchmark must contain:
straightforward questions;
conceptual misconceptions;
procedural errors;
ambiguous answers;
transfer problems;
misleading problems.

And ideally:

ADAPT shouldn't know the hidden answer key describing the student's misconception.

The benchmark evaluator knows it.

17. Attack #8 — "You're evaluating the AI using another AI."

Dangerous.

Suppose GPT evaluates whether ADAPT successfully detected a misconception.

Then GPT could simply agree with itself.

We need a better evaluation hierarchy.

18. Evaluation Layers
Layer 1 — Deterministic

For objective answers:

Correct / Incorrect
Layer 2 — Human evaluation

For:

misconception validity;
explanation quality;
challenge relevance.
Layer 3 — Structured rubric

For broader comparisons.

AI evaluation can help, but shouldn't be the only evidence.

19. Attack #9 — "What exactly is innovative?"

This is the hardest question.

Our answer cannot be:

"We use AI to personalize education."

Too generic.

It also can't be:

"We use multiple prompts."

Too weak.

The strongest claim is:

ADAPT turns learner responses into explicit diagnostic evidence and uses uncertainty-aware diagnosis to select the next challenge, rather than simply generating the next response conversationally.

And the actual innovation we demonstrate is:

A measurable adaptive learning loop.
20. Attack #10 — "Why not use a decision tree?"

This is where we should deliberately accept the criticism.

For narrow problems, a decision tree may be better.

So ADAPT should not claim:

"LLMs are always better."

Instead:

LLMs enable adaptive diagnosis when student responses are open-ended and misconceptions aren't easily encoded as fixed rules.

That's a much more defensible claim.

21. Attack #11 — "Is this really prompt engineering?"

Yes, if we build the workflow correctly.

But the prompts need to be designed as contracts, not vague instructions.

For example:

Diagnostic prompt

Input:

concept
student answer
expected reasoning
previous state

Output:

{
  "observations": [],
  "diagnoses": [],
  "confidence": 0,
  "recommended_test": ""
}

Then another prompt consumes that structured state.

That's legitimate prompt workflow engineering.

22. Attack #12 — "Why not just use one huge prompt?"

Excellent question.

This should become part of our benchmark.

Compare:

Baseline
ONE LARGE PROMPT

versus:

ADAPT
DIAGNOSIS
↓
STATE
↓
CHALLENGE SELECTION
↓
RESPONSE ANALYSIS

MISCONCEPTION TEST

ADAPTATION

Now we're actually testing whether workflow decomposition improves the tutoring process.

23. Attack #13 — "Does more workflow automatically mean better?"

No.

And we shouldn't build 15 nodes.

Our destruction test reveals that the workflow should be:

OBSERVE
 ↓
DIAGNOSE
 ↓
TEST
 ↓
UPDATE
 ↓
ADAPT

That's the conceptual core.

24. Attack #14 — "What happens if the learner doesn't want challenges?"

Important UX issue.

ADAPT shouldn't force a rigid interrogation.

The learner should be able to say:

"Explain it."

Then the system can provide a short explanation and follow it with:

"Let's see if that explanation resolved the gap."

The goal is adaptive learning, not endless quizzes.

25. Attack #15 — "What happens when the student is already an expert?"

The system should detect high performance quickly.

For example:

Challenge 1 → correct
Challenge 2 → correct
Challenge 3 → correct

Then:

Increase difficulty.

Eventually:

Mastery demonstrated.

This prevents wasting time on trivial questions.

26. Attack #16 — "What happens if the student keeps failing?"

ADAPT shouldn't simply lower difficulty indefinitely.

It should change strategy.

For example:

Hard question
      ↓
Easier question
      ↓
Still fails
      ↓
Change representation
      ↓
Visual explanation
      ↓
Micro-challenge
      ↓
Re-test

This makes representation adaptation important.

28. Attack #18 — "Is this over-engineered?"

Potentially.

Therefore our MVP will only demonstrate:

Difficulty adaptation
+
Misconception targeting
+
Representation change

We don't need every possible adaptation mechanism.

29. Attack #19 — "What could another team copy in 24 hours?"

A competitor could build:

ChatGPT
+

+
if wrong → easier question

Very easily.

Therefore our defense is:

They can copy the interface.
They can copy the idea.

But our competitive advantage in judging becomes:

We actually benchmarked the adaptive workflow against a baseline and can show the mechanism working on difficult learner scenarios.

This is important.

30. Attack #20 — "What would make me remember this?"

Not the dashboard.

Not the logo.

Not the LLM.

The moment should be:

The AI changes its teaching strategy because of something subtle in the student's answer.

For example:

Student:

"The recursion never stops because n keeps getting bigger."

ADAPT:

"Your answer suggests you're thinking about the recursive call correctly, but you're not tracking how n changes between calls."

Then:

Changing challenge type → trace the value of n.

That is memorable.

31. The Biggest Strategic Change

Our Phase 0 concept was:

Adaptive AI tutor.

That's too broad.

After destruction testing, the competition concept becomes:

AI-powered diagnostic learning loop

with:

uncertainty-aware misconception diagnosis + adaptive challenge selection.

That's considerably stronger.

33. The Three Core Innovations

I would now define the system around three pillars.

1. Diagnostic reasoning

What does this response tell us about the learner?

2. Uncertainty-aware diagnosis

How confident are we, and what evidence supports it?

3. Adaptive challenge selection

What should the learner do next to both learn and resolve uncertainty?

Everything else supports these three.

34. What We Should NOT Claim

This is important.

Do not claim:

❌ "ADAPT guarantees better learning."

❌ "ADAPT eliminates misconceptions."

❌ "ADAPT understands exactly what students know."

❌ "ADAPT is more intelligent than ChatGPT."

❌ "ADAPT provides personalized education for everyone."

❌ "Our AI detects learning styles."

❌ "Our AI scientifically measures mastery."

Instead:

✅ "ADAPT estimates learner state from response evidence."

✅ "ADAPT generates explicit misconception hypotheses."

✅ "ADAPT adapts subsequent challenges based on those hypotheses."

✅ "We evaluate whether this workflow improves learning outcomes compared with a single-prompt baseline."

35. The Competition Hypothesis — Revised

Our original hypothesis:

A structured adaptive tutor improves learning.

Too broad.

Revised:

We hypothesize that explicitly separating response analysis, misconception diagnosis, uncertainty estimation, and challenge selection enables an LLM tutor to produce more targeted learning interactions than a single-prompt tutor.

And then a second hypothesis:

We hypothesize that targeted challenges can improve performance on unseen transfer problems, not merely repeated practice questions.

Now we have something worth testing.

36. What Would Falsify ADAPT?

This is actually a strength.

ADAPT should be considered unsuccessful if:

Scenario A

Baseline produces equal or better learning gains.

Scenario B

ADAPT diagnoses misconceptions poorly.

Scenario C

ADAPT requires significantly more interactions without improving transfer.

Scenario D

Adaptation doesn't correlate with learner improvement.

Scenario E

The adaptive workflow is no more useful than a single well-designed prompt.

If these happen, our thesis is weakened.

That's okay.

A credible experiment is stronger than fake certainty.
